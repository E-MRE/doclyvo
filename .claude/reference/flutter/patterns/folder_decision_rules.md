# Folder Decision Rules

Where to put new code in the `lib/` tree.

---

## Feature Folder Layout

Every feature lives under `lib/features/<feature_name>/` and follows this structure:

```
lib/features/<feature_name>/
├── models/
│   ├── <entity>_model.dart         # EntityModel implementation
│   └── <entity>_model.g.dart       # generated by json_serializable
├── data/
│   └── repositories/
│       ├── <entity>_repository.dart         # abstract interface
│       └── remote_<entity>_repository.dart  # concrete implementation
└── presentation/
    ├── cubit/
    │   ├── <entity>/
    │   │   ├── <entity>_cubit.dart   # BaseCubit<State>
    │   │   └── <entity>_state.dart   # all 4 state classes
    ├── mixins/
    │   └── <screen_name>_state_mixin.dart  # private screen mixin
    ├── pages/
    │   └── <screen_name>_screen.dart       # StatefulWidget
    └── widgets/
        └── <feature_widget>.dart           # feature-specific widgets
```

## Decision: `app/widgets/` vs `features/x/presentation/widgets/`

### Put in `lib/app/widgets/` when:
- Used across 2+ features
- No dependency on a feature-specific model type
- Generic visual primitive: `BoxShimmer`, `CachedImage`, `BasicErrorContainer`, `LabeledSection`, `ImageCarouselSlider`
- DeveloperInfoText, SocialMediaIconButton, LinkText

### Put in `lib/features/x/presentation/widgets/` when:
- Used only in one feature
- Imports a feature model (e.g., `CampaignModel`, `CategoryModel`)
- Would create a cross-feature dependency if moved to `app/widgets/`

### Keep as private class in the same file when:
- Used only by one screen
- Named `_WidgetName` (underscore prefix)
- Is an implementation detail, not a reusable UI component

---

## Decision: `app/constants/` vs `core/utils/constants/`

### Put in `lib/app/constants/` when:
- Related to app-level configuration: endpoints, responsive breakpoints, misc app constants
- Examples: `AppConstants`, `EndpointConstants`, `ResponsiveConstants`

### Put in `lib/core/utils/constants/` when:
- Related to design system primitives used everywhere
- Examples: `Sizes`, `AppInsets`, `AppBorderRadius`, `EmptySize`, `SliverEmptySize`, `AppRoundedRectangleBorder`

---

## Decision: `app/utils/mixins/` vs `core/utils/mixins/`

### Put in `lib/core/utils/mixins/` when:
- Platform-level cross-cutting behavior: `ImageUrlCompleterMixin`, `JsonConverterMixin`, `PlatformAwareLauncherMixin`

### Put in `lib/app/utils/mixins/` when:
- App-level behavior tied to the app's DI or startup: `AppDependencyRegisterMixin`, `SafeStateMixin`

---

## Feature Folder Naming

Feature folders use `snake_case`. Strictly one folder per screen domain:

```
lib/features/home/        ← home screen and all its data
lib/features/category/    ← category browsing screen
lib/features/product/     ← product detail screen (future)
```

No `lib/features/shared/` or `lib/features/common/`. Cross-feature shared code goes into `lib/app/` or `lib/core/`.

---

## When to Use `part` / `part of`

This project uses `part` **only for generated files**:

```dart
// In model file
part 'banner_model.g.dart';
```

Never use `part` / `part of` for manual code organization. Use separate files with proper imports instead.

---

## New Constant Decision

Before hardcoding a number:
1. Check `Sizes.*` — is there a named size for it?
2. Check `AppInsets.*` — is there a named inset for it?
3. Check `AppBorderRadius.*` — is there a named radius?
4. If none match → add a new constant to the appropriate class; do NOT hardcode inline
